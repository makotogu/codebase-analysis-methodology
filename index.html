开场

你的处境：接手一个没人说得清的系统

文档缺失或过期

仅有的架构图是三年前画的，从画完那一刻就开始腐烂。没人敢保证它和当前代码一致。

命名和业务对不上

SettleService 实际干的是对账，真正的结算在 ClearingJob。命名漂移、历史包袱、口头约定俯拾皆是。

只有分散日志

没有 tracing、没有统一指标。运行时真相散落在各服务的日志文件里，没有一个地方能看到完整调用链。

测试不足，没人敢改

核心模块只有一两个老人敢动。直接重构等于裸奔，而"先补齐测试"又遥遥无期。

这不是个别现象，是存量系统的常态。方法论的前提就是接受这个常态——而不是先花一个季度"补基建"再开始分析。

开场

先认清两种注定失败的打法

漫游式阅读

从随机文件点进去，深度优先陷进细节，一周后什么也没沉淀。大型代码库 80% 的代码和你当前关心的问题无关——没有地图的阅读注定迷路。

对抗手段：建图

AI 幻觉式总结

让 LLM 概括架构，得到一份看似合理但没有任何文件路径支撑的文档。AI 会顺着命名编故事，而存量系统的命名恰恰经常和业务实际对不上。

对抗手段：证据等级

给牵头人的警示：你的团队成员和你自己都会自然滑向这两种模式。方法论的作用不是提供聪明技巧，而是提供纪律。

总纲

总框架：证据驱动的循环

01建图静态骨架
+ 运行时加权
02验证日志 / 断点
真实输出校准
03评估热点与痛点
变更耦合分析
04决策重构方向
变更 × 业务演进
05执行绞杀者模式
小步安全替换

这是循环，不是瀑布——执行中发现的新事实回流地图。知识沉淀（notes / glossary / rules）贯穿全程：Agent 没有记忆，笔记是下一轮分析的上下文，是一等公民而非副产品。

总纲

五条不可妥协的原则

1
证据驱动无 file:line 支撑的论断一律视为假设，禁止进入结论
2
笔记是一等公民地图、术语表、追踪记录是方法论的核心资产
3
以流为锚点围绕端到端可观察旅程组织阅读，不以文件为锚点
4
先榨干已有信号存量日志与 git 历史优先于补埋点
5
确定性优先采集和分析用 parser 与 git 挖掘；LLM 只做归因、摘要、错位探测这些模糊任务，且必须回填路径证据

第 5 条的深层含义：采集+分析层不依赖 LLM 也能跑——LLM 坏了、贵了，不影响数据积累；只有综合层是 LLM 密集的。

第一部分 · 建图

没有流量数据的地图是瞎的

没有流量数据的代码地图就像没有车流量的街道图——结构对了，但优先级是瞎的。

模块边界图

每个仓库/模块的用途、语言、构建系统、上下游。多仓库先画仓库间边界。

关键目录图

每模块 ≤10 个重要目录。生成代码、vendored 依赖、构建产物提前过滤。

端到端旅程图

一条可观察请求从入口到出口。以流为锚点：旅程的主路径有限，无关的 80% 自然被排除。

第一部分 · 建图

先榨干已有信号，再谈补埋点

五类躺着的数据，不改一行业务代码

  • 网关 / access log — 哪些接口真的有量
  • APM trace（如果有）— 真实调用链
  • error 日志密集处 — 直接当缺陷密度的代理指标
  • DB 慢查询日志 — 数据访问的热点和痛点
  • 异常堆栈聚合 — 高频故障路径

被低估的手段：生产覆盖率

采样式 profiler（JFR / async-profiler / eBPF）在生产跑一两个月，直接得到"哪些代码真的被执行"。

副产品极有价值：连续几个月从未执行的代码就是死代码候选。删死代码是 ROI 最高的重构——先把地图上不存在的街道擦掉，剩下的图才好看。

这些数据足以回答：哪 20% 的代码承载了 95% 的流量。

第一部分 · 建图

后台任务：比用户链路更好处理

第一步 · 静态建触发源清单

定时任务一定注册在某处：crontab、@Scheduled、xxl-job、k8s CronJob；MQ 消费一定有 topic 订阅。全部可 grep、可解析。

产出：触发源 → 入口函数（file:line）→ 声称用途。这张表是完备的——注册机制就那么几种。

第二步 · 分发点插桩一次

不给每个任务埋点。定时框架和 MQ 消费收口在一两个框架边界（调度 dispatch、consumer 基类）。

在这一个点加结构化日志，一次性拿到所有任务的执行频率、耗时、失败率。

这比给用户链路补埋点便宜一个数量级。有了"完备清单 + 执行权重"，后台地图往往比前台先完成。

不要为了分析先建全链路 tracing——那是季度级工程，会把分析卡死；这套办法成本是天级的。传播误差大的地方（分支、动态分发）恰恰是人工重点验证清单——又回到证据等级体系。

第二部分 · 证据体系

双轴证据：AI 能验证什么，不能验证什么

代码轴（AI 可自主推进）

等级含义
verified本地文件或命令确认，附 file:line
inferred从命名/结构/惯例推断，无直接证据
unverified需构建/运行/源码追踪验证

业务轴（只能由人推进）

business-confirmed 必须具名、带日期："据张三，2026-07"——业务理解会过时，来源和时间让它可审计、可更新。

AI 可以确认"函数 X 写了表 A"，但"表 A 是不是业务上的结算流水"只能由人确认。两轴正交，分别推进。

牵头人的红线：重构决策只允许建立在 verified + business-confirmed 的论断之上，其余论断先补证据。

第二部分 · 证据体系

glossary：复利的长期资产

# glossary.yaml - code_term: SettleService business_meaning: 实际处理的是对账，不是结算； 真正的结算在 ClearingJob owner: 张三 confirmed_by: 张三 confirmed_date: 2026-07 evidence: src/main/java/.../SettleService.java

三条使用纪律

  • glossary 是人工段，机器重跑任何分析都不得覆盖
  • 每次 Agent 会话开始时注入，让 AI 在已澄清的术语上不再犯错
  • 访谈产出的每个澄清都回填 glossary，而不是散落在聊天记录里

它是复利的：每澄清一个术语，之后所有分析都受益。这是牵头人应该最早建立的资产之一。

第二部分 · 证据体系

AI 角色反转：从解释者到错位探测器

四类要找的错位模式

  • 名为 query 却有写操作、名为 validate 却顺手改状态
  • 注释说的分支条件和实际代码不一致
  • 名为 X 却顺手干了 Y（职责溢出）
  • 同一个业务词在不同模块指不同东西（术语冲突）

闭环工作流

  1. 只跑热点模块（控制成本），AI 标记疑似错位
  2. 产出访谈问题清单——不是结论
  3. 人工访谈领域专家，回答高价值问题
  4. 回填 glossary，注入后续所有会话

不要问 AI"这段代码的业务含义是什么"——它只会顺着命名编。人的介入从逐行陪读变成聚焦、高杠杆的仲裁：每个回答都让后续 AI 分析更准。

第三部分 · 重构决策

热点分析是第一优先级

变更频率 × 复杂度排序

  • 复杂但三年没人动的模块 → 重构它几乎是纯浪费
  • 每周都改、每次改都出 bug 的 500 行函数 → 这才是真目标

叠加信号提精度：缺陷密度（error 聚合）+ 运行时热力图

AI 的角色：归因分析

"为什么这里频繁变更？"

  • 需求本身多变 → 不该动
  • 抽象切错了，每个需求都要动它 → 重构目标

核心主张：重构方向不是从代码里读出来的，是从"变更历史 × 业务演进方向"里算出来的。"让代码更干净"不能作为立项理由。

第三部分 · 重构决策

抽象方向由变更轴线决定，不由品味决定

哪些需求会一起来，哪些代码就应该被一起改到；如果现状做不到，说明抽象切错了方向。

找被切碎的概念

相距很远的文件总在同一 commit 被改 → 隐含概念被切碎，应收拢到一起。

找多轴线巨型模块

一个文件在毫不相关的需求里都被改（典型如巨型 service）→ 承担多个变更轴线，应拆。

不为假设的未来抽象

依据必须是已发生 ≥2–3 次的变更模式。存量系统最贵的债，往往是当年为不存在的未来做的抽象。

方法论立场：自底向上为主——AI 只出候选，人做裁决；目标架构可作远景参考，但每一步重构的立项依据必须是已发生的变更证据。

第三部分 · 重构决策

目标挂指标，提案有门槛

四类可用指标

类别指标示例（数据来源）
交付某类需求平均改动文件数、lead time（git + 需求系统）
质量热点模块缺陷密度、回归率（error 聚合、bug 系统）
认知新人上手时间；知识孤岛模块数（git 作者分布）
架构依赖规则违反数（依赖图 + 适应度函数）

提案最低证据门槛

  1. 热点/耦合数据 —— verified
  2. 业务含义确认 —— business-confirmed
  3. 收益假设 —— 明确写出赌的是哪个指标

三者缺一，提案退回补证据

知识孤岛值得单独盯：git 作者分布可直接算 bus factor。热点 × 孤岛 = 双重风险——既频繁变更，又只有一个人能改。

第四部分 · 梳理阶段

梳理不是理解任务，而是分类任务

Shopify 的做法

把 6000 个 Ruby 类列进一张大表格，人工逐个标注归属组件（orders / shipping / billing…）。

不需要读懂每个类的实现，只需回答"它属于哪个业务概念"。难度从不可能变成可管理：有分母（进度可算）、可并行、有完成态。

AI 改变了成本结构

  • LLM 批量提议标签，每条附置信度 + 证据（调用了谁、操作哪些表）
  • 人只仲裁低置信度和有争议的部分
  • T1 co-change 做标签一致性校验：总一起变更的文件应同标签，违反处要么标错、要么是真实架构问题

前置条件：先立标签体系——目标组件来自业务概念（订单/运费/计费）而非技术层次（MVC），由领域干系人共同给出，控制在几十个以内。

第四部分 · 梳理阶段

先止血，再梳理（Slack Project Duplo）

Stabilize六个月，只干两件事
Modularize组件化、边界划分
Modernize技术栈现代化

终结所有半途而废的迁移

Objective-C → Swift、直连 CoreData → 数据访问库……能收尾的收尾，不能收尾的至少冻结（禁止新代码使用旧模式）。

N 种写法收敛成一种

"Instead of multiple ways to do the same thing, we had a single correct way." 同一件事三种写法，一切扫描、归类、分析的成本都要乘三。

一致性是梳理的前提条件，不是梳理的结果。stalled migration 是隐形的分析税。另一层价值：Stabilization 先出成果，向组织证明项目能成，为后面更有野心的阶段挣到持续投入。

第四部分 · 梳理阶段

先归类让耦合暴露，而不是先解耦（Shopify）

big-bang PR：纯文件移动

Shopify 做的第一件事不是解依赖，而是一次性把全部文件按业务概念重排目录——零逻辑改动、自动化脚本生成，完备测试套件兜底。

目的只有一个：归类之后，跨组件调用从"看不见"变成"扎眼"。耦合可见了，解耦才有靶子。

代价（他们如实记录了）

git 历史被文件移动打断——GitHub 把 rename 当成删除 + 新建。

这正好印证 T1 git 挖掘的坑：必须用 --follow 或等价机制跨越这类大迁移，否则改名文件的历史断裂。

梳理难的一大原因是耦合不可见。物理归位是最便宜的可见化手段——先让代码的"住址"反映业务归属。

第四部分 · 梳理阶段

燃尽图与棘轮：把梳理变成可问责的进展

度量：两家共同做法

  • Slack：自动脚本数"剩余废弃模式数量"，配 dashboard 和 deadline，落后就重新调配资源
  • Shopify Wedge：每组件算隔离得分、列违规清单（跨组件非公开 API 调用、跨组件继承），看趋势
  • 度量脚本是 grep 级工作量，但把"感觉上的进展"变成可问责的进展

治理：三个机制

  • 专职团队——梳理不能是"大家有空时做的事"
  • 棘轮机制——存量违规豁免为 baseline，新增违规 CI 直接拦；违规数只许降不许升
  • 对上用数据拿授权——见下方三件套

Slack 给管理层的提案三件套：(1) 数据支撑的痛点 (2) 进度度量方案 (3) 各阶段失效模式预判——最少见也最值钱：把"项目可能烂尾"从隐忧变成被管理的对象。

第五部分 · 执行

表征测试 + 绞杀者模式

  1. AI 批量生成表征测试 —— 锁定现有行为：不管行为对不对，先如实记录。写"记录现状"的测试人类觉得枯燥，AI 做得又快又好，这是 AI 杠杆最高的场景之一
  2. 绞杀者模式小步替换 —— 新实现在旁边生长，流量逐步切换，旧代码逐步枯萎，任何一步都可回退
  3. 可观测性随重构增量生长 —— 替换某条链路时顺手把 tracing/指标埋进新代码，而不是重构前先做可观测性大工程
  4. 适应度函数守住成果 —— 重构方向确定后，把目标写成可执行断言进 CI，防止回退

存量代码库大概率测试不足，直接改等于裸奔。执行永远走这个套路。

第五部分 · 执行

适应度函数：把重构目标写成 CI 断言

依赖规则

"domain 层不得 import infra 层"——写成可执行断言，违反即 CI 失败。

模块体积上限

巨型 service 拆完后设体积红线，防止悄悄长回去。

热点分回归检查

重构目标挂的指标（如某模块热点分）纳入趋势监控。

时机上的重要修正：完整版最后做，但它的棘轮版本应该在梳理期就提前上线——存量违规先豁免为 baseline，新增违规直接拦，不等重构方向定了才上。

第六部分 · 工具箱

Java / Spring 的四个红利

actuator 对账

/actuator/mappings 给出运行时真实路由表，和静态清单 diff：静态有运行时没有 → 死入口；运行时有静态没有 → 普查漏洞。

Micrometer 白捡指标

有 actuator 则 http.server.requests 开箱即有——HTTP 入口的频率、耗时、状态码不用写一行插桩。第一步永远是查 pom 里有没有 actuator。

死代码检测几乎免费

-verbose:class 或 JFR 记录类加载，生产跑一两个月，从未加载的类就是死代码候选——经常能划掉两位数百分比。

T2.5 表映射：数据所有权

MyBatis XML / JPA 注解静态可解析出"每张表被谁读谁写"。拆模块的硬约束往往不是代码依赖而是数据所有权——一张表被五个模块写，代码拆得再干净也是假拆。

静态解析用 JavaParser / tree-sitter，不需要工程能编译通过——对老旧存量工程很重要。Spring 的坑：条件装配（@Profile / @ConditionalOn）会让静态清单里的入口在生产根本不激活，所以对账必须做。

第六部分 · 工具箱

分布式 / Dubbo 与 trace 三层决策

Dubbo 反直觉的好消息

  • 强类型接口比 HTTP 字符串 URL 好分析得多：接口 FQCN+version+group 是天然 join key，纯静态拼出跨服务调用图（T2.6）
  • 注册中心是白捡的运行时真相：静态 join 与 ZK/Nacos dump 对账，不写插桩就把证据从 inferred 升 verified
  • 跨仓库 co-change：按工单 ID 或发布窗口近似——一个需求总要同时改 A、B 两个服务，就是边界切错的铁证
  • 最恶劣的耦合是共享数据库表：调用图上看似解耦，实际是假拆

trace 三层决策

  1. 埋点层统一 OTel 标准（最重要）——OTel Java Agent 零代码自动埋点，避免被任何一家 APM 锁死
  2. 后端看运维能力，不看功能清单——SkyWalking / Tempo / Jaeger 都够用，别在选型上花太久
  3. tail-based sampling——错误全采、慢请求全采、正常流量低比例

立场澄清：反对的是手工全链路埋点（季度级）；自动埋点是周级成本，应尽早上。业务键进 span attributes 的手动埋点，放在重构替换链路时顺手做。

第七部分 · 多仓库联合分析

真实系统的单位是工作区，不是仓库

第一步永远是 repos.yaml

前端 x 个仓库、后端 y 个仓库、BFF、lib，都先放进同一张工作区清单：name / path / kind / language / service / api_client_dirs。

这张表就是多仓库分析的分母。覆盖率、遗漏检查、stable ID 都从这里开始。

stable ID 必须带仓库前缀

# 全局唯一，不再只看单仓库路径 web-portal::src/api/order.ts order-service::src/main/java/.../OrderController.java bff-mobile::src/routes/order.ts

单仓库工具仍然照常跑；新增的是工作区级的合并视图：API 边、RPC 边、共享表边、跨仓库 co-change，以及唯一一份跨前后端 glossary。

第七部分 · 多仓库联合分析

三类跨仓库边，静态可得性决定打法

RPC 边

后端 ↔ 后端。Dubbo 强类型接口是天然 join key：FQCN + version + group 静态 join，再与注册中心 dump 对账。

证据上限：对账后 verified

API 边

前端 → 后端。扫 axios/fetch/API client，路径归一化后与后端 entries.yaml 里的 HTTP 路由 join。

match：exact / prefix / fuzzy / unmatched

共享表边

任意 ↔ 任意。MyBatis/JPA 在所有后端仓库跑，合并成"表 × 服务"读写矩阵。

最高优先级假拆证据

API 边最容易骗人：前端 URL 是字符串，join 必须显式标置信度。`unmatched` 不是直接结论，而是后端下线、前端漏扫、网关前缀或动态拼接的验证队列。

第七部分 · 多仓库联合分析

跨仓库 co-change：工单 ID 优先，时间窗兜底

高质量信号：工单 ID

commit message 有需求/工单号规范（如 PAY-123）时，按工单聚合跨仓库变更集。

一个需求总要同时改 ≥2 个后端仓库，就是服务边界切错的铁证。

弱趋势信号：时间窗

完全没有工单规范时，才用"同一作者在 ±N 小时内多个仓库提交"近似。

噪音大，只用于仓库级趋势。不能下钻到文件级，也不能写成 verified 结论。

前端仓库与页面域对应后端长期强耦合通常是正常现象；值得警惕的是前端总和不属于它页面域的后端耦合，或多个后端仓库总被同一个工单一起改。

# 单仓库：当天得到三张 CSV python3 scripts/git_miner.py . \ --months 12 \ --out notes/t1 # 多仓库：加上工单 ID 跨仓库 co-change python3 scripts/git_miner.py repo-a repo-b \ --ticket-regex '[A-Z]{2,10}-\d+' \ --out workspace/t1

  • 时间衰减：上月变更权重大于一年前

产出 hotspot.csv / cochange.csv / ownership.csv

收尾

人机分工：各做各擅长的

AI / Agent

  • 并行探索：同时摸清配置加载、权限模型、写入路径几条线
  • 批量生成表征测试（枯燥但关键）
  • 错位探测：产出访谈问题清单
  • 归类标注提议：附置信度 + 证据
  • 候选清单 + 收益假设生成

人（牵头人与领域专家）

  • 裁决优先级、判断哪条线值得深入
  • business-confirmed 确认（具名+日期）
  • 访谈领域专家，回填 glossary
  • 仲裁低置信度标注与争议归属
  • 对上拿授权：数据支撑的痛点 + 度量方案 + 失效模式预判

表示形式上遵循"一份数据、两个投影"：人看 treemap / mermaid，模型读 stable ID + 显式边的卡片，都从同一数据层派生。永远不要手绘架构图——手绘图从画完那一刻就开始腐烂。

先定义分母，再跑工具，用证据说话

  4. 建 templates/ 里的 glossary 与 notes——人工段从第一天保护起来
  5. 选一条端到端旅程做第一次运行时验证，再把热点喂给 T7 访谈问题
