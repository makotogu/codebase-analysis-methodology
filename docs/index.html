核心问题

面对巨大的、缺少文档的存量系统

我们要回答什么？

如何用 AI/Agent 辅助把系统分析清楚，并据此决策重构方向？

这不是什么

  • 不是阅读技巧合集
  • 不是让 LLM 自由发挥写架构总结
  • 每个环节都有明确产出物、证据等级与人机分工

设计出发点

对抗两种最常见的失败

漫游式阅读

从随机文件深度优先陷进细节，一周后什么也没沉淀。80% 代码与当前问题无关——没有地图的阅读注定迷路。

对抗手段：建图

AI 幻觉式总结

让 LLM 概括架构，得到看似合理但无文件路径支撑的文档。AI 会顺着命名编故事，而存量系统命名往往与业务对不上。

对抗手段：证据等级

01 建图方法论

静态骨架 + 运行时加权

三张静态图

  • 模块边界图 — 仓库/模块用途与上下游
  • 关键目录图 — 每模块 ≤10 个重要目录
  • 端到端旅程图 — 以流为锚点，不以文件为锚点

运行时加权

  • 先榨干 access log、APM trace、error 聚合
  • 慢查询与生产 profiler 找真实热点
  • 后台任务：触发源清单完备可枚举
  • 未验证路径标为候选，写明验证手段

02 证据体系

代码事实 × 业务语义 双轴

代码轴（AI 可推进）

等级含义
verifiedfile:line 或命令输出确认
inferred从命名/结构推断，尚无直接证据
unverified需构建/运行/追踪验证

业务轴（只能由人推进）

business-confirmed 具名确认，带日期与来源

代码 verified ≠ 业务可信。重构决策只允许建立在 verified + business-confirmed 之上。

术语对照表（glossary）是复利资产——每澄清一个术语，之后所有分析都受益。

03 重构决策

方向从变更历史算出来

热点分析第一优先级

变更频率 × 复杂度排序。复杂但三年没人动的模块——重构 ROI 极低；每周都改、每次出 bug 的 500 行函数才是真目标。

抽象方向由变更轴线决定

  • 同 commit 共改的文件 → 隐含概念被切碎
  • 无关需求都改同一文件 → 承担多轴线，应拆分
  • 不为假设的未来做抽象——依据已发生 ≥2–3 次的模式

执行：绞杀者模式 + 表征测试，小步替换，可观测性随重构增量生长

核心原则

五条不可妥协的约束

1
证据驱动无 file:line 支撑的论断一律视为假设
2
笔记是一等公民地图、术语表、追踪记录是核心资产
3
以流为锚点围绕端到端可观察旅程组织阅读
4
先榨干已有信号存量日志与 git 历史优先于补埋点
5
确定性优先采集分析用 parser 与 git 挖掘；LLM 只做归因、摘要、错位探测，且必须回填路径证据
